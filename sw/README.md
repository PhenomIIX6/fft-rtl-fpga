# Проверка FFT по UART

`fft_uart.py` генерирует комплексные отсчёты с фиксированной точкой, передаёт
один блок на FPGA, получает ровно один блок результата и проверяет его.
Следующий блок отправляется после получения предыдущего. Скрипт также
сохраняет обмен в JSON и перепроверяет сохранённые ответы без подключения платы.

## Установка и первый запуск

Нужен Python 3.10 или новее. Единственная внешняя зависимость для UART —
pySerial. Модели, генератор и программные проверки используют стандартную
библиотеку Python; NumPy не требуется.

Из корня репозитория, в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r sw/requirements.txt
.\.venv\Scripts\python.exe sw/fft_uart.py --dry-run --capture captures/dry-run.json
.\.venv\Scripts\python.exe sw/fft_uart.py --replay captures/dry-run.json
```

`--dry-run` рассчитывает ответ программной моделью, кодирует и декодирует его.
Это проверка программного пути, а не доказательство исправности RTL или платы.
В JSON и в консоли этот режим явно помечен как `dry-run`; аппаратные времена
и пропускная способность для него не формируются.

Если `python` открывает Microsoft Store, используйте полный путь к установленному
Python. Уже созданное окружение запускается через `.venv\Scripts\python.exe`.

## Работа с платой

```powershell
.\.venv\Scripts\python.exe sw/fft_uart.py --list-ports
.\.venv\Scripts\python.exe sw/fft_uart.py --port COM3 --baudrate 115200 --N 512 --WIDTH 16 --INTEGER_WIDTH 2 --ROUND 1 --SATURATION 1 --RADIX_OUT_SCALE 1 --frames 10 --seed 42 --capture captures/fpga.json
```

Перед первым обменом сбросьте FPGA. Параметры FFT в командной строке описывают
**уже собранную прошивку** и должны совпадать с ней, включая параметры ROM.
Команд настройки FPGA через UART в существующей обвязке нет. UART работает
в режиме 8N1, без программного и аппаратного управления потоком.

В `de2_115.sv` назначены GPIO[0] для RXD и GPIO[1] для TXD; также нужна общая
земля. Перед аппаратной проверкой необходимо завершить обвязку платы:
в текущем дереве не сформирован сигнал `arst_n`, подключённый к `top`,
а реализация `clock_pll` и проект Quartus не включены в репозиторий.

Управление `tready` внутри FPGA не обеспечивает управление потоком на проводах
UART. Скрипт не посылает следующий блок, пока не получит ответ на текущий.
В протоколе нет заголовков, длины, номера блока, CRC или команды сброса.
Если байт потерян или обмен прерван, нужно сбросить FPGA перед новой попыткой.
Очистка буфера компьютера не восстанавливает счётчики упаковщика в FPGA.

По умолчанию неожиданные байты в RX-буфере считаются ошибкой.
`--discard-input` явно разрешает очистить буфер **один раз при открытии порта**;
это не команда сброса FPGA. Чтения и записи могут возвращать часть данных:
скрипт собирает полный ответ в пределах общего таймаута TX+RX. При ошибке
с `--capture` сохраняется в том числе полученная часть ответа.

## Аргументы

Полный список: `python sw/fft_uart.py --help`. Имена параметров FFT поддерживают
также варианты в нижнем регистре, например `--n`, `--width`, `--integer-width`.

| Аргумент | По умолчанию | Значение |
|---|---:|---|
| `--N` | 512 | Степень двойки от 8; ограничение снизу связано с адресацией ROM в RTL |
| `--WIDTH` | 16 | Биты одной компоненты; модель поддерживает 3–32 бита |
| `--INTEGER_WIDTH` | 2 | Целые биты **включая знак**; от 2 до WIDTH−1 |
| `--ROUND` | 1 | 1: округление к ближайшему с половинами к чётному; 0: усечение |
| `--TRUNCATION` | — | Синоним `--ROUND 0` |
| `--SATURATION` | 1 | 1: насыщение; 0: оборачивание при переполнении |
| `--RADIX_OUT_SCALE` | 1 | Сдвиг вправо после каждой стадии, от 0 до WIDTH |
| `--baudrate` | 115200 | Скорость UART, должна соответствовать прошивке |
| `--timeout` | автоматически | Общий таймаут записи и чтения одного блока, секунды |
| `--frames` | 1 | Число последовательных блоков |
| `--seed` | 1 | Seed отдельного генератора случайных чисел |
| `--pattern` | random | `random`, `zero`, `impulse`, `dc`, `tone` |
| `--amplitude` | 0.5 | Верхняя абсолютная амплитуда каждой входной компоненты |
| `--tone-bin` | 1 | Номер пика для `--pattern tone`, от 0 до N−1 |
| `--tolerance-lsb` | 0 | Допустимое расхождение каждой компоненты с целочисленным эталоном |
| `--twiddle-rom` | генерируется | Путь к точному `twiddle_factors.bin`, использованному при сборке |
| `--capture` | — | JSON с параметрами, входами, байтами, эталоном, ответом и метриками |
| `--replay` | — | Проверить сохранённые байты из JSON, используя его параметры и коэффициенты |

`--amplitude` задана в физических единицах фиксированной точки, а не как доля
полной шкалы. Генератор `random` равномерно выбирает целые коды для Re и Im
в симметричном диапазоне заданной амплитуды. Это исключает погрешность
преобразования случайных float перед передачей. Для остальных шаблонов вход
квантуется округлением к ближайшему, половины к чётному, независимо от `ROUND`
в FPGA. Непредставимые входы считаются ошибкой, а не молча обрезаются.

## Формат байтов

Пусть `F = WIDTH - INTEGER_WIDTH`. Значение одной компоненты равно
`signed_integer / 2**F`. Знак кодируется дополнительным кодом.

Слово комплексного отсчёта: `{Re[WIDTH-1:0], Im[WIDTH-1:0]}`.
По UART передаются байты этого **целого слова от младшего к старшему**.
Отсчёт занимает `ceil(2*WIDTH/8)` байт. Компоненты не выравниваются по байтам
по отдельности; при WIDTH=13 весь отсчёт занимает четыре байта.
Неиспользуемые старшие биты последнего байта заполняются нулями.

Для WIDTH=16 и INTEGER_WIDTH=2:

```text
1 + 0.5j -> Re=0x4000, Im=0x2000 -> слово 0x40002000 -> 00 20 00 40
```

И вход, и выход идут в естественном порядке. Перестановка битов адреса при
загрузке реализована внутри `ram_init_unit`; Python её не применяет к UART.

## Что именно проверяется

В проекте коэффициенты имеют **положительный знак** экспоненты:

```text
Y[k] = sum(x[j] * exp(+2*pi*i*j*k/N)) / 2**(RADIX_OUT_SCALE * log2(N))
```

Без квантования это соответствует
`numpy.fft.ifft(x) * N / 2**(RADIX_OUT_SCALE * log2(N))`.
Обычный `numpy.fft.fft(x)` использует другой знак. При SCALE=1 эталон равен
`numpy.fft.ifft(x)`. В шаблоне `tone` вход имеет отрицательную экспоненту,
поэтому пик должен появиться именно на положительном `tone-bin`.

`fft_model.py` рассчитывает два эталона:

1. **Целочисленный:** квантованные коэффициенты четверти окружности, их
   перестановки и смена знака как в ROM, ширина выхода умножителя 2*WIDTH,
   сложение, масштабирование, округление и насыщение/оборачивание на каждой
   стадии. `PASS` означает, что каждая компонента принятого ответа отличается
   от этого эталона не более чем на `tolerance-lsb`.
2. **Математический:** то же преобразование и масштабирование в комплексных
   числах Python. С ним рассчитываются RMSE, максимальная комплексная ошибка
   и SQNR. Эти метрики отражают также квантование и намеренное насыщение,
   поэтому сами по себе не определяют `PASS/FAIL`.

По умолчанию коэффициенты воспроизводят округление положительной четверти
окружности в C-генераторе. Для проверки конкретной прошивки лучше передать
её ROM через `--twiddle-rom`: это исключит различия библиотек вычисления
тригонометрических функций на границе округления. ROM сохраняется в capture
как полная целочисленная таблица, поэтому replay не зависит от внешнего файла.

Целочисленный эталон проверяет предполагаемую арифметику и не повторяет ошибки
RTL. В частности, в существующем `round_trunc_scale.sv` ветка `SHIFT_AMOUNT==1`
пишет непосредственно в `res`, оставляя `res_rounded` без присваивания.
Это затрагивает ROUND=1, F=1, SCALE=0. Такой набор может не собраться или дать
неопределённый ответ в RTL; программный эталон не считает это правильным.
Описание `SATURATION` в README подмодуля также перевёрнуто относительно RTL.

Усечение отрицательных значений повторяет арифметический сдвиг вправо,
то есть округление вниз, а не к нулю. При переполнении без насыщения результат
оборачивается в дополнительном коде.

## Метрики времени

Для реального UART выводятся время полного обмена и `N / roundtrip_seconds`.
Это пропускная способность **всего обмена**, включая UART, драйвер и Python.
Время чистого FFT-ядра этим способом не измеряется: нужен аппаратный счётчик
тактов или симуляция. При N=512, WIDTH=16 один блок занимает 2048 байт;
при 115200 baud, 8N1 номинальное время двух направлений — около 0.356 с.

`ideal_sqnr_db` в JSON равен `null`, если мощность эталона или ошибка нулевая;
поле `ideal_error_is_zero` различает случай нулевой ошибки.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s sw/tests -v
```

Программные проверки покрывают известные последовательности байтов,
невыравненную ширину, знаковые границы, округление, насыщение, оборачивание,
сравнение с независимым прямым DFT, шаблоны сигнала, частичные чтения/записи,
таймаут, отключение порта, JSON replay и обнаружение повреждённого ответа.
При установленном pySerial выполняется также тест его `loop://` транспорта.
Loopback подтверждает передачу байтов, но не выполняет FFT.

Для сквозной RTL-проверки нужен Verilator 5+, C++ compiler и GNU Make.
Тесты `test_rtl.py` запускают исходный `top.sv` с UART-передачей и приёмом,
а не подменяют FFT программной функцией. Каждый сценарий передаёт два блока
последовательно и сравнивает полученные байты с целочисленным эталоном.
Если Verilator отсутствует, эти проверки явно отмечаются как пропущенные.
В Linux достаточно установить Verilator в PATH; иначе задайте переменную
`VERILATOR` с путём к исполняемому файлу. В Windows сборке MSYS2 может
потребоваться `VERILATOR_ROOT`, пути к GCC/Make в PATH и каталог TEMP без
пробелов и кириллицы.

Локально проверено: 20 программных тестов и 8 сквозных сценариев в Verilator
5.050. RTL-сценарии охватывают N=8/16/32/512, WIDTH=8/13/16/32, оба режима
округления, насыщение и оборачивание, INTEGER_WIDTH=2/3, SCALE=0/1/2,
порядок частот и два последовательных блока. Для ускорения симуляции UART
использует PRESCALE=4 с сохранением формата 8N1. Аппаратная плата в эту
проверку не входит.

### Исправление выгрузки RAM в подмодуле

Сквозной тест исходного подмодуля `ff193111` выявил потерю отсчётов при
длительном `m_tready=0` со стороны UART. Для N=16, WIDTH=16 приходило
36 байт вместо 64. В `ram_export_unit.sv` адрес чтения продвигался без
резервирования места для результата, который ещё находился в синхронной RAM.
Когда FIFO заполнялся, этот результат отбрасывался.

Исправление резервирует место в FIFO уже при запросе чтения, учитывает
операцию в обработке и завершает блок после передачи всех N отсчётов.
Доступен переносимый патч `patches/0001-fix-ram-export-backpressure.patch`.
Для чистого клона с исходным подмодулем примените его из корня репозитория:

```powershell
git -C fft-rtl apply ../sw/patches/0001-fix-ram-export-backpressure.patch
```

Это локальное изменение файла в подмодуле; его указатель на commit не меняется.
Если исправление уже применено, повторно применять патч не нужно.
Патч хранится в родительском репозитории, чтобы его можно было перенести
независимо от локальных изменений в подмодуле.

Коды завершения: `0` — проверка прошла, `1` — ответ не совпал с эталоном или
capture содержит незавершённую транзакцию, `2` — ошибка аргументов/файла/UART,
`130` — прерывание пользователем.

Основные файлы:

- `fft_uart.py` — интерфейс командной строки, capture и replay;
- `fft_model.py` — формат, генерация, коэффициенты и два эталона;
- `uart_transport.py` — UART с ограниченным временем обмена;
- `tests/` — программные проверки и стенд для сквозной RTL-проверки.
